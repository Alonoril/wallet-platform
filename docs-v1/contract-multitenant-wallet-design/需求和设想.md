# EVM 多租户中心化钱包架构重构方案

生产级技术设计 · V2.0 · 2026-10-10

核心方案：CREATE2 确定性合约地址 + 用户独立 DepositVault + 统一 VaultManager + 批量归集 + 合约资金池 + 链下双重记账。

你的重构思路不仅可行，而且值得作为原中心化钱包项目的一期核心架构重新设计。与传统 HD Wallet（助记词派生）模式相比，最大的改变是：

用户充值地址不再由私钥控制，而是由部署在链上的智能合约控制；平台统一控制合约的资产转移权限，并由独立的 Gas 账户承担链上交易手续费。

这样可以彻底消除传统 ERC-20 充值归集过程中，必须先往每个用户地址补充 ETH、BNB 等原生币作为手续费的问题。

但有一个必须明确的技术边界：

合约归集并不是零 Gas，而是让用户充值合约不需要 Gas 余额。 由平台统一支付部署、归集和提现的 Gas，最终仍需要链上 EOA 交易发送者支付手续费。即使引入 ERC-4337 Gas 代付，也只是改变付费方，并没有消除链上执行成本。

### 链上必须分为四种合约

| 合约              | 数量          | 主要职责               |
| --------------- | ----------- | ------------------ |
| `DepositVault`  | 每用户每链一个     | 接受充值、持有资产、授权归集     |
| `VaultFactory`  | 每链每版本一个     | 计算地址、创建用户合约、原子初始化  |
| `VaultManager`  | 每链一个或按安全域分组 | 验证归集权限、执行批量归集、控制暂停 |
| `TreasuryVault` | 每链每资金池一个    | 接收归集资金、管理资金流出、执行提现 |

这里不推荐直接让 `TreasuryVault` 同时承担合约部署、归集编排、提现、升级和所有管理权限。

应该让 TreasuryVault 只负责保管和授权转出资金，VaultManager 负责归集，VaultFactory 负责创建。

如此可以防止归集账户权限泄露后直接控制热钱包全部资产。

此外，还应独立部署 `VaultImplementation`（用户合约逻辑模板）、`AccessManager/Timelock`（治理权限）等基础组件。

## 三、核心设计：CREATE2 用户充值地址

这是整次重构中最关键的技术。

### 3.1 为什么不用助记词也能生成充值地址？

在传统模式下：

```
Mnemonic
  └─ HD Wallet
      └─ Private Key
          └─ Public Key
              └─ EOA Address
```

而新模式：

```
Wallet ID + Salt
        │
        ▼
VaultFactory 地址
        +
VaultImplementation 创建字节码
        │
        ▼
      CREATE2
        │
        ▼
预先计算 DepositVault Address
        │
        ▼
分配给租户用户作为充值地址
```

CREATE2 的地址计算公式是：

\\[ A=\operatorname{last20}\left( \operatorname{keccak256}\left( 0xff\parallel F\parallel S\parallel \operatorname{keccak256}(I) \right)\right) \\]

其中：

- \\(F\\)：部署合约的 Factory 地址。
- \\(S\\)：32 字节 Salt。
- \\(I\\)：合约部署所使用的完整 `init_code`。
- \\(A\\)：最终的用户充值地址。

此公式来源于 EIP-1014。它允许在真正执行合约部署之前，先确定合约地址。

### 3.2 最重要的优化：生成地址时根本不部署合约

一个充值地址的生命周期

按需部署

1. ALLOCATED — 地址已分配

   后台计算 CREATE2 地址，写入数据库，返回给租户。此时链上尚无用户合约，也没有部署 Gas。
2. FUNDED_UNDEPLOYED — 有资金，未部署

   用户将 ETH 或 ERC-20 发送到预计算地址。资产可以存在于尚未部署合约的地址上。
3. DEPLOYING — 首次归集时部署

   Relayer 调用 Factory，创建真实 DepositVault，同时完成归集。
4. ACTIVE — 已部署，可持续复用

   后续充值无需重新部署，直接由 VaultManager 发起归集。
5. RETIRED — 停止分配新用途

   旧地址仍可收到外部转账，必须长期保留监控及恢复归集能力。

注意：有余额但没有合约代码的 CREATE2 预计算地址，是正常且可行的状态。 EVM 的合约创建冲突规则主要检查目标地址是否已有非零 nonce 或合约代码，而不是仅凭地址余额判定冲突。

### 3.3 租户 ID 与用户 ID 如何生成唯一地址？

不建议直接把外部提供的 `tenant_id + user_id` 拼接后用于 Salt。

建议采用独立的内部标识：

```
Tenant UUID
   │
External User ID
   │
   ▼
平台内部 User UUID
   │
   ▼
Wallet UUID（全局唯一，随机生成）
   │
   ▼
walletKey = keccak256(
    abi.encode(
        DOMAIN,
        walletUUID,
        walletVersion
    )
)
   │
   ▼
salt = keccak256(
    abi.encode(
        walletKey,
        vaultVersion
    )
)
   │
   ▼
CREATE2 Address
```

需要满足：

1. `tenant_id + external_user_id` 在租户范围内唯一，并映射到不可变的内部用户标识。
2. 充值地址分配操作必须是数据库事务，具备幂等性。
3. 每条链的 `chain_id + address` 建立全局唯一约束。
4. Salt、Factory 地址、Implementation 版本、创建字节码哈希永久保存。
5. 对外不暴露能够直接关联用户身份的递增标识或明文用户 ID。

随机的 Wallet UUID 用于避免用户身份被简单枚举；它本身不是资产控制密钥，也不能作为链上授权依据。

另外，必须建立一个独立的 Address Registry 作为地址分配的唯一真实来源。不能依靠用户 ID 在不同版本的部署逻辑中重复计算后，假定一定得到相同地址。

CREATE2 地址还会受到 Factory 地址及 `init_code` 影响。升级合约实现或者更换 Factory，往往意味着新一代用户充值地址也会变化，因此需要显式的地址版本管理。

### 3.4 用户合约选用 ERC-1167，还是可升级代理？

我推荐：

DepositVault 采用固定实现版本的 ERC-1167 克隆合约；不采用每个用户单独配置的可升级代理。

ERC-1167 将用户合约执行委托给固定的逻辑实现地址，合约本身只部署少量字节码。

Ethereum Improvement Proposals



理由如下：

| 维度     | 固定 ERC-1167 Clone | Beacon / ERC-1967 可升级代理 |
| ------ | ----------------- | ----------------------- |
| 创建成本   | 通常更低              | 通常更高                    |
| 单个用户状态 | 极少                | 视实现而定                   |
| 升级方式   | 新版本部署新地址          | 可升级逻辑                   |
| 批量升级风险 | 较低                | 同时影响大量用户                |
| 应急修复   | 需要迁移或旧合约恢复路径      | 可升级修复                   |
| 适用情况   | 简单的充值与归集          | 功能复杂、持续变化的钱包            |

充值合约的功能越少，越应该追求不可变性。

不过 ERC-1167 本身并不会让逻辑代码天然安全。它会将调用转发到固定的实现地址，因而该实现地址的代码和依赖必须经过严格审计，且不能在同一实现下偷偷加入可变的升级机制。

我建议所有旧版本合约逻辑永久保留；以后升级使用 `VaultFactoryV2 + DepositVaultV2`，旧地址继续支持归集。对于发现严重漏洞的旧版本，应提供事先审计过的暂停与资产迁移路径，不能指望通过 `SELFDESTRUCT` 删除旧合约并原址重建。EIP-6780 已显著限制这种做法。

## 四、用户充值合约 DepositVault 的设计

一个用户的 DepositVault 不应该是完整的智能账户，也不应该支持用户自主签名、DEX 交易、任意合约调用等功能。

它本质上是一个受限的资产收款容器。

### 4.1 核心接口

以下是建议的合约接口规范，不是未经审计即可部署的完整实现：

```
interface IDepositVault {
    // 平台统一管理合约
    function manager() external view
        returns (address);

    // 归集目标所属的资金池
    function poolId() external view
        returns (bytes32);

    // 归集原生币
    function sweepNative() external
        returns (uint256 amount);

    // 归集指定 ERC20
    function sweepERC20(address token) external
        returns (uint256 amount);
}
```

设计要求：

- `receive()` 必须支持原生币充值，且不能依赖复杂逻辑。
- `sweepNative()` 只能由可信 Manager 调用。
- `sweepERC20()` 只能转给该 Vault 所属的授权 Treasury。
- 不提供 `execute(address target, bytes data)` 这种任意执行能力。
- 不提供任意 `delegatecall`、无限授权或任意修改收款账户的功能。
- 使用 `SafeERC20` 兼容返回 `bool` 或无返回值的常见 ERC-20 实现。
- 对外部 Token 调用采取重入保护和 Gas 限制策略。

OpenZeppelin 的 `SafeERC20` 已经封装了标准与部分非标准 ERC-20 的返回值处理，适合直接作为合约基础组件。

[image](https://www.google.com/s2/favicons?domain=https://docs.openzeppelin.com\&sz=32)

OpenZeppelin Docs



### 4.2 为什么不需要用户私钥？

假设用户 A 的充值合约地址为：

`0xDepositVaultA`

合约中：

```
function sweepERC20(address token)
    external
    onlyManager
{
    uint256 amount =
        IERC20(token).balanceOf(address(this));

    IERC20(token).safeTransfer(
        treasury,
        amount
    );
}
```

这是归集逻辑的简化表达。

当平台执行归集时：

```
Relayer EOA
    │
    │ 支付 Gas
    ▼
VaultManager.batchSweep(...)
    │
    │ 调用用户合约
    ▼
DepositVaultA.sweepERC20(USDT)
    │
    │ 当前代币持有人就是合约地址
    │ 调用 USDT.transfer(...)
    ▼
TreasuryVault
```

Token 合约会检查转账方是谁。

此时调用 Token 的是 `DepositVaultA`，也就是 Token 的持有人。因此它有权把自己持有的 USDT 转出去。

整个过程：

- 不需要用户私钥。
- 不需要向用户合约地址转 ETH。
- 不需要先调用 ERC-20 `approve()`。
- 不需要使用 `transferFrom()`。
- Gas 由最外层的 Relayer EOA 承担。

这是新方案解决原有 ERC-20 归集问题的根本原理。

### 4.3 用户合约应当使用极简状态

如果每创建一个用户合约，都在 Storage 中写入：

```
address owner;
address manager;
address treasury;
bytes32 userId;
bytes32 tenantId;
bool initialized;
```

不仅增加 Gas，还增加初始化与权限管理的攻击面。

建议优先探索 OpenZeppelin 的 `cloneDeterministicWithImmutableArgs`：

将 Manager、资金池标识等必要参数作为不可变克隆参数，而非每次都写入 Storage。OpenZeppelin 已提供相应部署和预计算接口。

[image](https://www.google.com/s2/favicons?domain=https://docs.openzeppelin.com\&sz=32)

OpenZeppelin Docs



但最终是否比传统 Clone + 少量初始化 Storage 更省钱，必须通过实际 Gas Benchmark 决定。不能只因为使用 immutable args 就假定总成本更低。

尤其要注意：创建和初始化必须具有不可被抢占的原子安全性。任何外部账户都不能在 Factory 部署合约后，抢先把 Vault 初始化为攻击者控制的地址。

## 五、VaultFactory：安全地生成和管理上百万个地址

Factory 应该设计成长期稳定、参数不可随意变化的合约。

### 5.1 核心接口

```
interface IVaultFactory {
    function predictVault(bytes32 walletKey)
        external view
        returns (address);

    function deployVault(bytes32 walletKey)
        external
        returns (address vault);

    function isVault(address vault)
        external view
        returns (bool);

    event VaultDeployed(
        bytes32 indexed walletKey,
        address indexed vault,
        uint32 version
    );
}
```

`isVault()` 是系统希望提供的逻辑能力，底层可以通过部署登记或 CREATE2 参数验证实现。

Factory 必须确保：

1. 允许部署的 Implementation 是固定且经过验证的代码。
2. Manager、归集目标及授权信息由平台可信配置决定，而非任意请求调用者提供。
3. 地址的预计算结果与实际部署地址逐字节一致。
4. 用户合约初始化在同一交易中完成。
5. 相同 Wallet Key 重复请求不能产生不同资产控制关系。
6. 部署失败可以安全重试，已部署的合约不能重复初始化。

值得强调：公开部署本身不一定是不安全的。

即使别人抢先调用 Factory，只要合约地址的控制权和归集目标已经在部署逻辑中固定，也不会因为部署者不同而改变资产所有权。

但一期建议限制部署权限，避免恶意账户大量触发无意义的部署流程。

### 5.2 资产已经充值，但合约尚未部署时怎么办？

这是生产中必须设计的一种正常状态。

假设用户向尚未部署的地址转入：

- 10 USDT
- 0.2 ETH

平台通过 Indexer 检测到对应资产后，判断是否达到归集阈值。

达到条件后执行：

```
Manager.batchDeployAndSweep(...)
          │
          ▼
Factory.deployVault(walletKey)
          │
          ▼
验证部署地址与预计算地址相同
          │
          ▼
Vault.sweepNative()
          │
          ▼
Vault.sweepERC20(USDT)
          │
          ▼
TreasuryVault
```

原生币和 ERC-20 可以在同一次外部交易中归集。

这时要注意链上事件的区别：

- 未部署时的普通 ETH 充值，不可能由 DepositVault 主动发出 `Deposited` 事件。
- 普通 ERC-20 转账不会自动调用收款 Vault 的函数，因此通常只能通过 Token 合约的 `Transfer` 日志检测。
- 合约内部的原生币转账需要交易追踪和余额核验，不能只依赖顶层 `tx.to`。

所以用户 Vault 并不负责对充值行为自动记账。充值发现与最终入账必须由链下 Indexer 和 Ledger 完成。

## 六、VaultManager：生产级批量归集引擎

这部分是新方案的性能核心。

### 6.1 Manager 不应该直接拥有随意转移全部资产的权限

理想模型为：

```
VaultManager
    │
    ├── 只能调用已登记 Vault
    │
    ├── 只能归集允许的 Token
    │
    ├── 只能归集到已授权 Treasury
    │
    ├── 只能使用归集相关函数
    │
    └── 不具备提现到任意外部地址的权限
```

这样，即使执行归集的 Relayer 私钥泄露，攻击者最多尝试把资产归集到平台本身的合法 Treasury，而无法单凭这个权限把资金打到自己的钱包。

这要求链上强制验证归集目标，而不能仅在 Rust 服务中做判断。

### 6.2 批量归集接口

推荐使用任务数组的统一接口：

```
struct SweepTask {
    bytes32 walletKey;
    address token; // address(0) 表示原生币
}

interface IVaultManager {
    function batchDeployAndSweep(
        SweepTask[] calldata tasks
    ) external;

    function batchSweep(
        SweepTask[] calldata tasks
    ) external;
}
```

这里应当配套独立的链上授权、暂停状态、Token 白名单、资金池隔离及失败恢复实现。

批量交易执行方式：

Relayer 提交一笔批量归集交易

例如 50 个用户 Vault 的 USDT 归集

Vault 001

成功

Vault 002

成功

Vault 003

失败

Vault ...

成功

Vault 049

成功

Vault 050

成功

合法资金统一转入 TreasuryVault

失败任务进入重试队列，不阻塞其他 Vault

示意图：单个 Vault 的失败必须由 Manager 在各子调用层面隔离，不能简单使用一个要求全成功的批量循环。

### 6.3 必须支持部分成功

假设一批 100 个用户：

- 99 个地址正常。
- 1 个地址持有的 Token 被发行方冻结，`transfer()` 失败。

如果普通循环中任何一次 revert 都导致整笔交易回滚，其他 99 个用户也无法归集。

因此建议采用：

Manager 对每个 Vault 进行受限外部调用，并分别记录成功与失败。

每个任务独立捕获错误，失败不影响已成功执行的子调用。但仍然属于同一笔 EVM 交易：如果最外层交易最终整体回滚，之前的成功也会一起回滚。

生产实现还需要防止恶意 Token 消耗过多 Gas、制造超大返回数据、重入调用或拖垮整个 Batch。

因此需要：

- 单任务 Gas 上限与整批 Gas 上限。
- 单任务调用隔离、可控的失败返回数据。
- 每个 `(vault, token)` 对应的业务任务幂等。
- 已处理任务不得因为重试而重复产生账务影响。
- 交易广播前 `eth_call` 模拟以及 Gas 估算。
- 通过实际执行结果和链上余额核对归集金额。

### 6.4 不要把批量大小写死

不建议永久固定每批 100 个地址。

真正影响 Gas 的变量包括：

- 当前 Token 合约的转账实现。
- 是否首次创建 DepositVault。
- Token 地址是否有复杂黑名单逻辑。
- TreasuryVault 是否执行额外的接收逻辑。
- 当前链的 Gas 限制。
- EVM 主网与各 L2 的计费模型。

正确做法是让 Sweep Scheduler 动态确定 Batch：

\\[ N\_{\text{batch}}= \max\left\\{ N: G\_{\text{estimate}}(N) \le G\_{\text{target}} \right\\} \\]

其中 `G_target` 应低于链的实际执行上限，预留估算误差与状态变化空间。生产中可以从较小批次开始，根据每条链实测逐渐提高。

## 七、归集 Gas 最优化：不能只考虑节约手续费

这是需要纠正一个容易出现的架构误区：

部署用户合约本身也要 Gas。因此新架构不是在任何情况下都比 EOA 归集便宜。

### 7.1 对比旧方案

| 操作            | HD Wallet 旧方案  | CREATE2 合约新方案    |
| ------------- | -------------- | ---------------- |
| 创建充值地址        | 不需要 Gas        | 不需要 Gas          |
| 接收 ERC-20     | 用户支付充值 Gas     | 用户支付充值 Gas       |
| 充值地址归集 ERC-20 | EOA 发起转账       | Manager 调用 Vault |
| 充值地址需要原生币     | 需要             | 不需要              |
| 给用户地址补 Gas    | 可能需要           | 不需要              |
| 第一次归集         | 直接签名转账         | 可能需要创建合约         |
| 后续归集          | EOA 再次签名转账     | 合约归集             |
| 批量归集          | 多笔外部交易，或引入额外机制 | 单笔外部交易内批量调用      |
| 控制密钥          | 每地址独立私钥        | 统一管理合约权限         |

### 7.2 新方案的成本模型

设：

- \\(G_d\\)：首次部署用户合约的 Gas。
- \\(G_s\\)：一次用户合约归集的执行 Gas。
- \\(G_b\\)：每个批次固定基础 Gas。
- \\(N\\)：批次中归集的用户数。
- \\(K\\)：单个用户合约生命周期内归集次数。

那么新方案平均每次归集的 Gas 近似为：

\\[ G\_{\text{new}} \approx \frac{G_d}{K} +G_s +\frac{G_b}{N} \\]

旧 EOA 模式则近似为：

\\[ G\_{\text{old}} \approx G\_{\text{ERC20-tx}} +G\_{\text{funding}} \\]

这里的 `G_funding` 是原生币补充成本的摊销值，并非每次必然重新补 Gas。

结论：

- 对只有一次小额充值、以后不再使用的用户，首次部署合约的成本可能让新方案更贵。
- 对重复充值的活跃用户，部署成本被摊销，批量执行和免补 Gas 的优势更明显。
- 对 EVM L1，部署成本必须重点核算。
- 对低 Gas 成本的 L2，新方案在工程管理上的优势通常更容易体现。
- Batch 可以摊薄一笔交易的固定成本，但不能消除每个 Vault 的 Token 转账执行成本。

因此不能在没有实测的情况下承诺减少 50% 或 80% 的总 Gas。

### 7.3 推荐加入智能归集调度策略

归集不应该是“有余额就立即扫”。

应该综合余额、Gas、资金需求与风险计算优先级。

最终 Scheduler 建议使用以下原则：

优先级一：安全与流动性。 热钱包余额不足、用户金额达到高风险阈值或安全策略要求立即归集时，优先执行。

优先级二：经济性。 根据 Gas/资产价值比例判断是否值得执行，避免为几美分的充值支付高额部署费。

优先级三：时间 SLA。 不能因为 Gas 一直偏高就无限期拒绝归集；应设置最长等待时间、异常告警与人工审批机制。

优先级四：批量优化。 尽量按 Chain、Token、TreasuryPool 和 Vault 版本分组，提高批量执行稳定性。

## 八、热钱包 TreasuryVault：必须与归集控制权分离

我认为这部分是整个架构的安全核心。

如果只设计一个具备无限转账权限的热钱包合约，由它管理所有用户充值合约、执行归集和提现，确实可以工作。

但是这个合约会变成巨大的单点风险。

建议采用以下资金控制模型：

```
                  平台治理多签
                      │
                Governance Safe
                      │
            ┌─────────┴─────────┐
            ▼                   ▼
      AccessManager          Guardian
            │                   │
       授权 / 限额          紧急暂停
            │                   │
            └─────────┬─────────┘
                      ▼
               VaultManager
                      │
                 归集权限
                      │
          DepositVault A/B/C/...
                      │
                      ▼
             TreasuryVault Pool
                      │
          ┌───────────┴────────────┐
          ▼                        ▼
    Withdrawal Policy          Cold Safe
          │                        │
          ▼                        ▼
      外部提现用户            冷资产存储
```

### 8.1 为什么建议多个 Treasury，而不是全平台一个？

原有平台要求多租户，所以资金模型必须考虑租户间风险隔离。

我推荐采用 共享管理层 + 分资金池的 Treasury 模式。

例如：

| 层级           | 隔离方式        | 说明           |
| ------------ | ----------- | ------------ |
| 逻辑账户         | 每租户每用户独立    | 账本、余额、风控完全隔离 |
| DepositVault | 每用户独立       | 充值资金可归属、可定位  |
| TreasuryPool | 租户专属或多个租户共享 | 按客户等级与风险等级划分 |
| Cold Vault   | 按资产规模与策略隔离  | 降低热钱包单点暴露    |
| Gas Relayer  | 按链/权限池分组    | 独立 Gas 预算与密钥 |

一期不一定需要为每个小租户都部署独立 Treasury，但应该在架构上支持这种能力。

高资金量租户建议使用专属 Treasury，避免一个资金池的合约问题波及全部租户。

### 8.2 TreasuryVault 最少需要的能力

```
interface ITreasuryVault {
    // 接收原生币
    // receive() external payable

    // 按授权请求执行提现
    function executeWithdrawal(
        Withdrawal calldata request,
        bytes calldata authorization
    ) external;

    // 冷钱包资金调拨
    function transferToCold(
        address token,
        uint256 amount
    ) external;

    // 紧急暂停资金流出
    function pauseWithdrawals() external;
}
```

对应的内部要求：

- 归集入金不需要与提现授权绑定。
- 提现必须有链上可验证的授权。
- 资金调拨、提现、管理员操作使用不同权限。
- 高风险操作使用多签、时间锁或额外审批。
- 每个资金池有独立的资产余额、额度和暂停策略。
- 不开放任意外部调用功能给普通操作员。

热钱包最好不是无限储备的资金总库，而是受额度管理的支付流动性池。

例如，链上资金分布可以设计为：

```
DepositVaults
    │
    ▼
Treasury Hot Pool
    │
    ├── 预留提现流动性
    │
    ├── 执行已授权用户提现
    │
    └── 超额资产自动调拨
              │
              ▼
         Cold Safe
```

冷钱包建议优先采用成熟的多签体系，而不是重新编写一套通用的多签资金保管合约。Safe 本身支持多签、模块与 Guard，但自定义模块的权限同样属于高风险审计范围。

### 8.3 Treasury 地址如何升级？

这里存在一个很重要的设计取舍。

如果每个 DepositVault 把 Treasury 地址永久写死，那么归集目标的安全性很高，但 Treasury 更换后，旧用户合约可能无法直接归集到新地址。

如果 DepositVault 允许 Manager 任意指定新 Treasury，那么 Manager 被攻破就可能导致所有用户资产被重定向。

我的建议是：

Vault 绑定固定资金池身份，资金池的 Treasury 变更由独立治理权限控制，并采用时间锁及紧急暂停机制。

也可以在早期版本直接绑定固定 Treasury 地址，通过旧 Treasury 到新 Treasury 的迁移完成升级。

在生产落地前必须选定其中一种模式，并明确资金池合约损坏时的恢复路径，不能在系统上线后再临时设计。

## 九、提现设计：链下审核与链上授权双重防线

合约托管钱包最容易出重大资金事故的环节不是充值，而是提现。

不能让服务端简单调用：

```
Treasury.transfer(token, to, amount)
```

就完成转账。

否则持有执行权限的应用服务器、Relayer 或其密钥泄露，都可能直接导致资金损失。

### 9.1 推荐提现业务流程

1. 租户发起提现

   通过 HTTP API 提交租户订单号、用户、网络、资产、金额、目标地址和幂等键。
2. Ledger 冻结可用余额

   使用数据库事务锁定资产，把可用金额转为提现预留金额，防止重复提现。
3. Risk Engine 审核

   检查身份权限、地址风险、金额限额、频率、租户额度、黑名单和异常行为。
4. Withdrawal Authorizer 授权

   由隔离的 MPC/HSM 签名服务生成受限提现授权，不让业务服务直接持有资金签名密钥。
5. Relayer 广播链上交易

   Relayer 调用 TreasuryVault，只支付 Gas，Treasury 在链上验证提现授权、Nonce、额度及期限。
6. 确认并完成账务结算

   Indexer 解析实际执行结果，确认后将提现预留余额正式扣减，失败或取消按规则释放。

### 9.2 使用 EIP-712 进行提现授权

建议签名数据结构：

```
struct Withdrawal {
    bytes32 requestId;
    bytes32 poolId;
    address token;
    address to;
    uint256 amount;
    uint256 nonce;
    uint256 deadline;
}
```

EIP-712 Domain 至少绑定：

```
name              = "Milon Custody Treasury"
version           = "1"
chainId           = 当前 EVM Chain ID
verifyingContract = 当前 Treasury 地址
```

还需要在合约中维护 `usedRequestId` 或可靠的 Nonce 消耗机制。

注意，EIP-712 定义的是结构化消息哈希与签名方法，并不会自动提供业务级的防重放保护。Nonce、请求唯一性与过期检查仍须自行实现。

[image](https://www.google.com/s2/favicons?domain=https://eips.ethereum.org\&sz=32)

Ethereum Improvement Proposals



例如授权请求中规定：

```
Request ID:  0x...
Asset:       USDT
Amount:      500000000
Destination: 0xUser...
Pool:        Pool-03
Nonce:       10242
Deadline:    2026-10-10T12:00:00Z
```

以上 `Amount` 假设 USDT 为 6 位小数，表示 500 USDT；只是数据结构示例，不是真实提现订单。

Relayer 不能在不使签名失效的情况下替换目标地址、金额、资产或资金池。

进一步建议在链上设置资金转出硬限额。这样即使一把 Authorizer 签名密钥被盗，攻击者也不能无限制地转出资金。

高额提现还可以要求双重授权或治理多签。

### 9.3 批量提现也必须支持

正常运营中，同一时间可能有成百上千笔提现。

可以让 Treasury 支持：

```
batchWithdraw(
    Withdrawal[] requests,
    Signature[] authorizations
)
```

但批量提现需要更加谨慎。

提现与归集不同：提现必须严格防止重复、超额和目的地址变化。

每一笔提现都要单独验证：

- `requestId`
- `nonce`
- `deadline`
- `token`
- `destination`
- `amount`
- `poolId`

当一笔失败时，可以按任务进行隔离处理，但必须保证其他任务不会因为失败处理逻辑而绕过授权。

链下 Withdrawal Engine 同时负责多 Relayer 的 Nonce 分配、交易加速、替换广播和重试恢复。不能因为交易长时间 pending，就重新创建一个不同 `requestId` 的提现请求，否则可能造成双重付款。

### 9.4 内部转账尽量不上链

平台类似支付宝，多个租户业务用户之间可能存在大量转账。

如果账户余额都由平台托管，内部用户转账并不需要在区块链上执行。

例如：

```
Tenant A / User 1001
        │
        │ 内部转账 100 USDT
        ▼
平台 Ledger 双重记账
        │
        ▼
Tenant B / User 2008
```

整个过程由原子数据库事务完成，保证资产负债关系一致。

用户需要真正提币到外部地址时，才发起链上提现。

这种内部净额结算所节约的 Gas，往往比逐笔优化链上归集更重要。

## 十、Ledger：用户余额绝对不能直接等于 Vault 的链上余额

这是生产级中心化钱包与普通区块链钱包最大的区别。

用户把 100 USDT 充值到自己的 DepositVault，平台检测并确认后记账。

稍后 VaultManager 把 100 USDT 归集到 Treasury。

归集发生后，用户在平台中的余额依然是 100 USDT。

链上地址余额已经变成 0，但用户对平台的债权并没有减少。

因此必须将两者完全分离：

```
链上资产：
DepositVault + Treasury + Cold Wallet

                   ≠

用户可用余额：
平台内部 Ledger

         通过双重记账与资产负债校验关联
```

### 10.1 推荐采用双重记账

以用户充值 100 USDT 为例。

简化会计示例，实际科目和法定会计处理需要结合业务所在地要求确定。

| 业务事件      | 借方               | 贷方              |
| --------- | ---------------- | --------------- |
| 充值最终确认    | Vault 托管资产 +100  | 用户资产负债 +100     |
| Vault 归集  | Treasury 资产 +100 | Vault 托管资产 -100 |
| 用户内部转账 30 | 用户 A 负债 -30      | 用户 B 负债 +30     |
| 提现实际完成 20 | 用户负债 -20         | Treasury 资产 -20 |

冻结余额、提现预留、平台费用、待处理充提都应有独立科目或状态。

关键要求是：

- 每个业务事件只产生一次有效记账效果。
- 一次记账包含平衡的借贷分录。
- 每个租户的账户与资产负债独立。
- 所有金额以最小单位整数存储，禁止使用浮点数计算资产金额。
- 对冲正、重组、异常恢复采用追加补偿记录，不删除原始财务历史。

- 原生币内部转账的交易 Trace。

## 十一、多租户冻结与风控应该如何设计？

冻结和解冻本质上是平台账务权限控制，而不是修改用户充值合约的地址所有权。

建议分三层实现。

| 层级       | 冻结方式                     | 适用场景         |
| -------- | ------------------------ | ------------ |
| 用户账户     | Ledger 禁止余额转出            | 普通业务冻结、余额预留  |
| Vault 归集 | Manager 拒绝对应 Vault 的自动归集 | 可疑或被调查入金     |
| Treasury | 暂停指定池或指定资产转出             | 严重风险、合约或密钥事件 |

普通业务冻结通常只需要在 Ledger 中完成。

如果是可疑入金，则不仅不应增加可提现余额，也应允许将资金留在隔离的 DepositVault 中，或者在符合政策时归集到专门的 Quarantine Treasury。

需要特别强调两个限制：

第一，冻结不能阻止外部用户向某个 EVM 地址转账。 它只能阻止平台认可这笔充值或转出相关资产。

第二，已经归集到共享 Treasury 的资产无法仅凭用户地址重新区分出对应的链上 Token 份额。 此时冻结主要是对账本债权的冻结。对需要链上物理隔离的资金，应在归集前就进入独立资金池。

冻结状态应由权威的链下风控系统记录；对于要求链上强制执行的冻结，应在 Manager 或 Treasury 增加对应授权检查，不能单纯依赖 Scheduler 自觉跳过任务。

## 十二、必须重点审计的安全风险

智能合约钱包替代 HD Wallet 后，用户私钥管理风险会降低，但攻击面会转移到合约实现、管理权限、资金池和系统签名服务。

以下风险属于上线前的阻断项。

| 风险              | 可能后果           | 强制防护                     |
| --------------- | -------------- | ------------------------ |
| Factory 初始化抢跑   | 攻击者控制预充值 Vault | 原子初始化、固定控制参数             |
| CREATE2 参数变化    | 充值资产无法按预期取回    | 固定字节码版本、离线与链上双重校验        |
| Vault 任意执行漏洞    | 用户资产被直接转走      | 禁止任意 Call / Delegatecall |
| Manager 权限失控    | 批量非法归集         | 归集目标链上约束、最小权限            |
| Treasury 提现授权泄露 | 热钱包被盗          | EIP-712、硬限额、多签与暂停        |
| ERC-20 重入       | 绕过余额或状态检查      | ReentrancyGuard、受限调用     |
| 恶意 Token        | 拖垮归集、伪造充值      | 资产白名单、Gas 上限、事件验证        |
| 重放与重复提现         | 重复付款           | Nonce、Request ID、幂等账务    |
| Reorg           | 虚假余额、重复记账      | 最终性校验、可冲正账本              |
| 多租户隔离失败         | 租户间资产错记        | 租户强隔离、账本约束、独立资金池         |

重入与访问控制是 Ethereum 官方安全文档明确强调的核心防御事项。

### 12.1 一个容易忽略的重大问题：恶意 Token

如果平台支持 ERC-20，不应该允许租户传入任意 Token 合约地址，就直接充值入账。

因为 ERC-20 合约可以包含自定义逻辑，某些代币还存在：

- 转账税和扣费机制。
- Rebase 导致余额自动变化。
- 黑名单、暂停、升级、冻结。
- 非标准返回值。
- 恶意或不规范的 `Transfer` 日志。
- 调用时异常消耗 Gas。
- 转账前后余额与预期金额不一致。

一期建议只支持经过审查、明确批准的 ERC-20。

到账金额和归集金额应以可验证的资产实际变化为依据，而不能无条件相信日志中的转账金额。

对于 Fee-on-Transfer、Rebasing 等特殊代币，建议一期直接拒绝支持，后续作为独立资产适配能力开发。

### 12.2 不要默认兼容所有 NFT

虽然你的 Vault 地址理论上也可能收到 NFT，但 ERC-721 的安全转账机制涉及接收合约接口。

例如 `safeTransferFrom` 在目标地址已部署合约时，通常要求其实现 `IERC721Receiver`；未部署合约地址与已部署合约地址的接收行为可能不同。

[image](https://www.google.com/s2/favicons?domain=https://docs.openzeppelin.com\&sz=32)

OpenZeppelin Docs



所以一期明确支持原生币和经过审核的 ERC-20 即可。

不应将 NFT、ERC-777 风格回调资产或复杂 Token 自动纳入统一归集逻辑。

### 12.3 合约部署前的资产恢复必须演练

CREATE2 方案最危险的运维事故之一是：

平台已经把大量未部署地址发给用户，后来却发现 Factory 部署参数不匹配或部署逻辑存在缺陷。

这可能导致有资金的地址无法成功部署受控合约。

因此必须建立一套生产不可绕过的验证机制：

```
为用户预计算地址
       │
       ▼
确认 Factory 存在且代码哈希正确
       │
       ▼
确认 Implementation 正确
       │
       ▼
核对 CREATE2 计算结果
       │
       ▼
确认 Factory 仍具备部署能力
       │
       ▼
地址写入 Registry
       │
       ▼
向外部发放地址
```

还必须在测试网络对以下场景进行真实恢复测试：

- 先充值 ETH，再部署和归集。
- 先充值 USDT，再部署和归集。
- 未部署地址持有多种 Token。
- Factory 重复部署请求。
- 部署成功但归集失败。
- RPC 中断后任务恢复。
- Relayer 私钥轮换。
- Manager 暂停后恢复。
- Treasury 迁移。
- FactoryV1 升级到 FactoryV2 后，旧地址仍能归集。

这些测试直接决定用户资金是否有可能永久被锁住。

## 十三、Gas Relayer 与密钥管理

新架构不再为每个用户维护 EOA 私钥，但仍然需要少量平台密钥。

建议至少划分五个安全域。

| 密钥 / 权限               | 功能          | 权限要求         |
| --------------------- | ----------- | ------------ |
| Governance Safe       | 合约治理、权限变更   | 冷多签、时间锁      |
| Guardian              | 紧急暂停        | 独立硬件密钥       |
| Withdrawal Authorizer | 签发提现授权      | MPC/HSM、风险策略 |
| Sweep Operator        | 发起归集        | 只能调用受限归集方法   |
| Relayer EOA           | 广播交易、支付 Gas | 低余额、可轮换      |

特别注意：

Relayer EOA 的私钥不应拥有直接控制 Treasury 资产的权限。

即使 Relayer 被入侵，攻击者最多消耗受限 Gas 预算，或者调用已经获得独立授权的操作。

权限控制建议基于 OpenZeppelin 的 `AccessManager` 和必要的治理延迟机制设计。

[image](https://www.google.com/s2/favicons?domain=https://docs.openzeppelin.com\&sz=32)

OpenZeppelin Docs



同时应实现：

- 每条链独立的 Relayer 池。
- 单个 Relayer 独立的 Nonce 管理。
- Gas 余额不足报警与补充。
- EIP-1559 手续费预测和交易替换。
- 相同业务请求的交易幂等与结果恢复。
- HSM/KMS 权限审计及密钥轮换。
- 热钱包余额实时监控。
- 关键资金池异常时自动触发保护模式。

一期不建议引入 ERC-4337 作为基础设施依赖，因为当前方案是平台中心化托管，不需要让最终用户自主发起智能账户交易。直接使用受限 EOA Relayer 已经能够解决 Gas 统一支付的问题。

ERC-4337 的 Paymaster 可以提供 Gas 代付，但会增加 EntryPoint、Bundler、Paymaster 等额外组件和验证逻辑。

## 十四、第三方业务平台的安全集成

由于你原来的目标是允许多个第三方系统通过 HTTP API 集成钱包，所以合约重构后 API 层仍然需要独立的安全设计。

建议使用：

```
Tenant Application
      │
      ▼
HTTPS / mTLS
      │
      ▼
API Gateway
      │
      ├── Tenant Identity
      ├── Request Signature
      ├── Timestamp / Nonce
      ├── Idempotency
      ├── Rate Limit
      └── Permission Check
      │
      ▼
Wallet Application Services
```

请求签名至少绑定：

`tenant_id + method + path + body_hash + timestamp + nonce`

避免攻击者重放签名请求、替换提现目的地址或跨租户调用。

如果业务方要求应用层额外加密，可以使用 JWE。签名密钥和 JWE 加密密钥应分开管理，通过 `kid` 支持分阶段轮换。

Webhook 也必须签名，并采用持久化投递、重试与失败恢复机制。

### 推荐 API

| API                              | 说明           |
| -------------------------------- | ------------ |
| `POST /v1/wallets`               | 幂等创建用户钱包及账户  |
| `GET /v1/wallets/{id}/addresses` | 查询链上充值地址     |
| `GET /v1/balances`               | 查询可用、冻结及预留余额 |
| `GET /v1/deposits`               | 查询充值历史与确认状态  |
| `POST /v1/transfers`             | 平台内部转账       |
| `POST /v1/holds`                 | 冻结或预留余额      |
| `POST /v1/holds/{id}/release`    | 解冻           |
| `POST /v1/withdrawals`           | 提现申请         |
| `GET /v1/withdrawals/{id}`       | 提现状态查询       |

第三方业务不能直接指定 `VaultManager`、`TreasuryVault`、Salt 或任意合约执行参数。

这些属于平台内部资产控制平面，不是租户 API 的能力。

## 十六、生产上线验收标准

生产级可用不能只等于“合约可以成功部署、充值、提现”。

建议将以下指标作为正式上线门槛。

| 维度    | 验收要求                               |
| ----- | ---------------------------------- |
| 地址正确性 | 批量预计算与真实部署结果 100% 一致               |
| 地址隔离  | 不同钱包记录无地址冲突、无资金池误绑定                |
| 充值入账  | 重复事件、重复消费不得造成重复入账                  |
| 财务一致性 | 双重记账持续平衡，异常均可追溯                    |
| 归集权限  | 任何普通操作员不能改变合法归集目的地                 |
| 提现安全  | 无有效授权不可提现；请求不可重放                   |
| 密钥安全  | 核心资金密钥不以明文进入业务服务                   |
| 归集稳定性 | 单个 Vault 或 Token 失败不拖垮整个队列         |
| 故障恢复  | 数据库、RPC、Worker 重启后可安全恢复            |
| 压力测试  | 至少验证百万地址注册和高并发充提场景                 |
| 安全审计  | 合约独立审计、模糊测试和关键不变量测试                |
| 灾难恢复  | Factory、Signer、Ledger、Indexer 故障演练 |

特别推荐将这些安全不变量写入 Foundry Invariant Tests：

1. 所有合法 Sweep 的目的地址都必须属于授权资金池。
2. 任意非管理账户都不能使 Vault 资产流向未授权地址。
3. 相同提现请求在任意重试组合中最多成功执行一次。
4. 归集不能创造或增加用户 Ledger 余额。
5. 暂停提现后，普通执行路径不能继续转出资产。
6. 任意 Vault 部署地址都必须匹配其登记的 CREATE2 地址。
7. 链上余额、待归集资产、资金池余额与 Ledger 的差额都能够解释并追溯。

正式主网上线前，还需要两项非代码工作：独立安全审计，以及确认项目在实际运营司法辖区的托管、反洗钱、客户资产隔离和牌照合规要求。

## 十七、实施优先级与迁移路线

## P0

确定地址与控制权模型

锁定 Factory / Implementation / Manager / Treasury 的依赖关系，完成 CREATE2 地址预计算、懒部署、收款与权限隔离的安全原型验证。此阶段不处理复杂业务 API。

## P1

完成充值、归集与 Gas 基准测试

实现 Native/ERC-20、批量归集、部分失败恢复、归集经济策略。针对每条目标链比较旧 EOA 模式和 CREATE2 模式的真实 Gas。

## P2

完成生产级资金账本和提现

建设 Ledger、EVM Indexer、EIP-712 提现、权限隔离、风控、资金池余额管理、链上重组处理及对账。

## P3

多租户安全集成和上线

完成租户 API、安全通信、幂等回调、审计、密钥生命周期、灾难恢复、主网小额灰度和逐级限额开放。

如果原有 HD Wallet 已经在线上使用，则旧地址不能立即关闭。应同时运行旧 EOA 充值监听与新 CREATE2 合约监听，对外新用户切换到新地址，旧地址通过受控迁移策略逐步退出。

## 十八、最终推荐架构与三个不可妥协的设计原则

最终推荐组合

## CREATE2 + ERC-1167

用户独立充值地址 · 懒部署

## VaultManager + Batch Sweeper

统一 Gas · 安全归集 · 故障隔离

## Isolated Treasury Pools

分级资金池 · 有限授权 · 冷热分离

## Rust Ledger + Risk + Signer

租户账务隔离 · 双重记账 · 提现风控

原则一：用户 DepositVault 永远只是受限收款容器。 不应变成一个功能复杂的智能钱包。越简单、越不可变、越容易审计，越适合管理海量充值地址。

原则二：归集权限和提现权限必须物理分离。 VaultManager 可以把资金收进合法 Treasury，但绝不能凭借归集权限把资产转到任意地址。

原则三：链上资产控制与链下账本必须各自独立。 链上合约负责保管与转移，Ledger 负责用户资产权益，Risk Engine 负责冻结和审批，Indexer 负责事实核验。

### 还有一个必须在编码前验证的架构假设

我最建议先投入精力解决的，并不是编写 Vault 合约，而是完成一套 跨链、跨 Token、跨用户活跃度的归集成本 Benchmark。

因为新方案消除的是用户地址补充原生币的操作，并不保证第一次归集的链上 Gas 一定低于 HD Wallet 模式。

正确的工程决策应当建立在两组结果之上：

- 安全结果： 未部署地址预充值、Factory 可靠性、资产恢复、Manager 授权边界可以通过审计及故障测试验证。
- 经济结果： 对 1 次、5 次、20 次以上重复充值的不同用户，以及 Ethereum、BSC、Arbitrum 等目标链，量化两种架构的累计 Gas 成本。

如果这两项验证通过，我支持将你设想的合约充值模型作为一期主架构，而不是保留大量 HD 钱包派生地址，再把合约归集作为附加功能。

最终要实现的系统形态是：平台可以管理数百万个用户充值地址，但无需保管数百万把用户私钥，也无需给每个充值地址单独补充 Gas，同时保持资金归集、租户账务与提现风控的严格隔离。

这才是这次重构最有价值的目标。


- 合约还要考虑一个重要的问题：一笔“黑钱”转进了合约，还未归集；另一种情况是“黑钱”已经被归集了。这两种情况要怎么处理都需要在方案中重点考虑，并给出可行性方案

# EVM 托管钱包 V2.1：黑钱识别、资金隔离与归集污染防控方案

生产级架构补充 · AML/KYT 风控 · DepositVault 资金隔离 · Treasury 风险保护

这个问题非常关键。它甚至比 CREATE2 地址派生和归集 Gas 优化更应该优先解决。

因为在中心化托管钱包里，最危险的情况不只是收到风险资金，而是风险资金被自动归集到共享热钱包后，与其他用户的正常资产混在一起，导致整个资金池面临冻结、调查、流动性中断或合规处置风险。

因此，我建议在原方案上进行一次重要的架构升级：

把“先检测充值，再自动归集”改成“充值识别 → 资金风险审查 → 授权归集 → 隔离资金池 → 热钱包资金池”，并建立归集后风险追溯和紧急冻结能力。

这里的“黑钱”需要分两类判断：一类是已被可靠识别、依法应当阻断或冻结的资金；另一类只是链上分析工具提示可能涉及高风险交易的资金。后者需要进一步调查，不能仅靠一个风险评分就认定资产违法。FATF 也明确将异常交易模式、资金来源、交易方画像等视为风险指标，而非单独的违法定论。

## 一、两个场景的处理结论

| 场景                         | 风险程度  | 建议处置                                  |
| -------------------------- | ----- | ------------------------------------- |
| A：黑钱进入用户 DepositVault，尚未归集 | 可控性较高 | 立即停止入账或冻结可用额、阻止归集、保留原地址资产、启动审查        |
| B：黑钱已归集到 Treasury，但尚未使用    | 高     | 暂停受影响资金池的相关资产转出、锁定对应风险敞口、追踪资金来源和受影响范围 |
| C：黑钱已归集，且资金池已发生其他提现        | 极高    | 紧急风险处置、分析链上流向、隔离尚存敞口、评估已付款项与报告义务      |

两条最重要的原则：

第一，风险资金未归集时，尽量不要移动它。对于尚未明确法律性质的可疑资金，先审查；对于依法必须冻结的资金，按照适用法律和监管要求控制，不能擅自退回或转移。

第二，风险资金已经归集后，不能简单地再转出相同金额，就声称“黑钱已经被清洗或隔离”。ERC-20 和 ETH 都是同质化资产，同一合约地址中的相同资产没有可以按存入交易逐个区分的独立币编号。必须通过资金流追踪、账本负债隔离与依法许可的链上资产隔离共同处理。

这也是为什么不建议把所有 DepositVault 的资金直接归集到唯一的共享热钱包。

## 二、重新设计资金架构：增加风险隔离层

原设计：

```
用户 DepositVault
        │
        ▼
    VaultManager
        │
        ▼
共享 TreasuryVault
```

现在建议改成：

用户 DepositVault

用户独立合约 · 接收 ETH / ERC-20

KYT / AML Risk Engine

交易来源检查 · 链上溯源 · 制裁筛查 · 策略判定

通过审核

风险命中

ClearingVault

已审核资金的缓冲结算池

Risk Hold

保留在原 DepositVault，停止移动

再次确认

依法批准的特殊处置

TreasuryVault

业务热钱包 · 提现与资金调拨

QuarantineVault

隔离保管池 · 仅合规授权转移

Risk Hold 默认不发生链上资产转移；QuarantineVault 仅用于法律允许或要求的隔离保管，不能自动将命中风险的资金转入。

这意味着原架构需要额外引入四项核心能力：

- Risk Engine： 对每一笔充值进行风险分析，而不是仅检查用户或充值地址。
- SweepAuthorization： 未得到有效风险授权的充值，不允许进入正常归集流程。
- Risk Registry： 链上强制控制哪些 Vault / Token 可以归集，哪些必须冻结。
- Treasury Incident Control： 已归集资金发现问题后，可以立即暂停相关资金池转出并进行追溯和隔离。

这四项应视为生产版本的 P0 能力，而不是上线后的风控增强功能。

## 三、场景 A：黑钱进入 DepositVault，但尚未归集

这是最好处理的情况，也是必须优先利用合约架构解决的场景。

### 3.1 举例：正常充值和黑钱充值进入同一个合约

假设：

```
Tenant A / User 1001
         │
         ▼
DepositVault: 0xAAA...
         │
         ├── TX1：+100 USDT（正常）
         │
         └── TX2：+20 USDT（命中高风险）
                     │
                     ▼
             Vault 余额 120 USDT
```

此时平台识别 TX2 是涉及被制裁地址的入金，或者存在其他依法应阻断的风险。

应该如何处理？

我建议默认冻结整个 Vault 的该 Token 归集，而不是直接把 100 USDT 扫走、20 USDT 留下。

原因在于：标准 ERC-20 的 `balanceOf(vault)` 只会返回 120 USDT，不存在 `balanceOf(vault, txHash)` 这种按充值来源划分的链上余额。

即使合约支持：

```
sweepERC20(token, 100e6);
```

也只能实现“转出数量 100”，无法从 Token 合约层证明转出去的是 TX1 对应的正常资金。

因此存在两种隔离：

| 隔离类型              | 能否实现   | 含义                      |
| ----------------- | ------ | ----------------------- |
| 数额隔离              | 可以     | 冻结 20 USDT 对应的账务额度      |
| 物理地址隔离            | 可以     | 将风险资金保留在独立 Vault        |
| 同一 ERC-20 余额按来源区分 | 不能原生实现 | 不能从余额中指定 TX1 的币与 TX2 的币 |
| 有证据支持的部分资金释放      | 有条件可行  | 必须经过风险、法律和账务审查          |

这实际上暴露了“一个用户永久只有一个充值地址”的局限。

### 3.2 第一阶段：立刻锁定风险

建议系统按以下顺序处理：

1. 风险识别

   Indexer 记录 TX2 的 `chainId / token / txHash / logIndex / from / to / amount / blockHash`，Risk Engine 生成风险事件与证据。
2. 链下冻结

   将该笔充值标记为 `RISK_HOLD`。如果已入账，则冻结相关可用额度，并检查此前是否已经发生内部转账或提现。
3. 撤销归集调度

   禁止 Sweep Scheduler 新建任务；取消尚未广播的任务，对已广播任务追踪最终结果。
4. 链上强制阻断

   对 `(vault, token)` 设置 `HOLD`。Manager 必须拒绝该资产的普通归集请求，不能仅依赖数据库状态。
5. 建立合规案件

   保留资金在原 Vault，等待人工复核、资金来源证明、法律意见或有权机关指令。

这里有一个细节：`HOLD` 不需要停止用户合约接受充值，因为 ERC-20 直接转账通常不会调用接收合约，无法阻止转入。即使一个合约拒绝普通 ETH 转账，也无法确保所有形式的 ETH 转入都被拒绝。

### 3.3 未部署的 CREATE2 合约怎么办？

反而更简单。

如果用户只是拿到了预计算地址，Vault 还未真正部署：

```
未部署 CREATE2 地址
       │
       ├── 收到 100 USDT
       └── 收到 20 USDT 风险资金
                │
                ▼
        风控禁止首次部署归集
                │
                ▼
        资产保留原链上地址
```

不需要立即执行任何链上交易。

数据库中的状态变为：

```
address_state = FUNDED_UNDEPLOYED
risk_state    = HOLD
sweep_state   = BLOCKED
```

但是，不部署不等于资产已经在链上被冻结。预计算地址中的资产实际上暂时无法使用，只是平台选择不触发部署。

Factory 后续的部署与归集仍必须受权限控制。要防止某个被盗 Relayer 或其他执行账户直接部署并归集这些资金。

最安全的方式是：

- 地址计算本身可以开放查询。
- 部署后的资金控制权由固定、可信的合约权限决定。
- 正常归集必须持有有效风险授权。
- 风险冻结状态可以覆盖此前发出的归集授权。

### 3.4 风险解除后如何处理？

建议提供严格的业务状态：

```
DETECTED
    │
    ▼
RISK_HOLD
    │
    ▼
UNDER_REVIEW
    │
    ├── CLEARED
    │       └── 恢复符合授权条件的归集
    │
    ├── CONTINUE_HOLD
    │       └── 继续冻结
    │
    └── LEGAL_DISPOSITION
            └── 按合法指令执行特定处置
```

如果审查认定是误报，才能恢复正常的入账与归集。

如果必须长期冻结，则资金可以继续留在该 DepositVault 中，不必强制转到 QuarantineVault。

对于受到法律冻结要求的资金，是否可以转入专门的隔离钱包，必须根据适用法律、账户控制和审批要求决定。

例如，美国 OFAC 的数字资产冻结指导允许在满足控制条件时选择分别冻结钱包，或把被阻断资产整合到受控钱包。它同时要求只有获得相应授权或法律限制解除后，才能解冻或归还被阻断资产。这是美国适用主体的具体规则，不能直接当作其他司法辖区的通用授权。

### 3.5 一个真正有价值的改进：高风险场景使用一次性充值合约地址

原方案是：

`tenant_id + user_id → 一个永久有效的 DepositVault`

我建议改为支持两个模式：

| 模式   | 地址模型                  | 适用业务              |
| ---- | --------------------- | ----------------- |
| 标准模式 | 每用户、每链一个长期充值地址        | 日常小额、高频重复充值       |
| 隔离模式 | 每次充值订单一个独立 CREATE2 地址 | 大额业务、高风险交易、特殊监管要求 |

例如：

```
User A
   │
   ├── DepositVault #1
   │      └── Deposit Order 001：100 USDT
   │
   ├── DepositVault #2
   │      └── Deposit Order 002：20 USDT 风险资金
   │
   └── DepositVault #3
          └── Deposit Order 003：50 USDT
```

此时第二笔风险资金不会和第一笔资金共存在同一个充值地址内。

第一笔和第三笔可以独立审核和归集，第二笔保留在原地址。

这是从链上地址层面实现资金风险隔离，而不是依靠一个余额数字做区分。

代价是一次性地址数量更多、首次合约部署 Gas 更高、归集复杂度增加。它也不能阻止别人向任意地址恶意转账，因此仍然需要风险检测。

推荐一期同时支持两种地址模型，而不是强制所有用户都使用一次性地址。 这样正常用户可以保留归集成本优势，大额和敏感业务则可以选择更强的风险隔离。

## 四、场景 B：黑钱已经归集到 Treasury

这是最需要重视的问题。

假设平台资金分布如下：

TreasuryVault Pool A

示例：USDT 资金池

# 1,000,000 USDT

账面链上余额

其他入金：999,000 USDT

事后发现风险：1,000 USDT

红色仅表示事后识别的风险敞口金额，不表示链上的 USDT 可以逐枚识别为红色或绿色。

一笔 1,000 USDT 的风险充值已经从用户 Vault 归集到了这个价值 100 万 USDT 的资金池。

随后 KYT 服务发来一条新告警，指出该入金涉及严重风险。

现在是否可以只冻结 1,000 USDT，其余 999,000 USDT 继续提现？

技术上可以进行对应金额的账务预留和支付限额控制，但不能直接认为这种处理已经满足全部法律冻结要求，也不能保证代币发行方不会限制整个资金池地址。

例如，Circle 公布的 USDC 条款和风险披露说明，其保留对特定地址实施区块链层面限制的能力。在某些情况下，涉及的合约地址可能整体受到转账限制，而不是仅仅针对某笔存款设置一个逻辑冻结数字。

### 4.1 发现已归集风险资金后的第一反应

我建议设计独立的 `Treasury Incident Control`。

正常情况下：

```
TreasuryVault
    └── WITHDRAWAL_ENABLED
```

接到严重告警后：

```
TreasuryVault
    └── ASSET_HOLD
          │
          ├── 暂停受影响 Token 提现
          ├── 停止新的资金调拨
          ├── 禁止自动进入其他资金池
          ├── 锁定相关提现任务
          └── 等待风险范围评估
```

如果风险涉及管理密钥、合约控制权或整个资金池，也应支持 `POOL_PAUSED`，暂停整个池的资产流出。

这里建议采用先保护、后缩小冻结范围的策略。

不能因为风险充值只占资金池的 0.1%，就自动决定只冻结 0.1%。

但也不应永久冻结其他用户的正常资产。事件调查后，需要根据风险性质、法律义务和实际资金敞口尽快释放未受影响的资金及服务能力。

### 4.2 追踪风险资金的完整路径

系统必须能够从原始充值事件追踪到所有后续资产操作。

例如：

```
TX-001  用户向 DepositVault 充值 1,000 USDT
   │
   ▼
DEPOSIT-001
   │
   ▼
RISK-DECISION-001
   │
   ▼
SWEEP-JOB-001
   │
   ▼
TX-002  DepositVault → ClearingVault
   │
   ▼
TX-003  ClearingVault → TreasuryVault
   │
   ▼
TREASURY-POOL-A
   │
   ▼
后续资金调拨 / 提现流水
```

这里的链上归集不会自然保留原始 `txHash` 的业务关联。

因此，平台必须自己维护如下关系：

```
deposit_id
    -> screening_decision_id
    -> sweep_job_id
    -> sweep_tx_hash
    -> treasury_pool_id
    -> settlement_batch_id
    -> downstream_transfers
```

建议所有归集相关合约都发出可审计的事件，例如：

```
event SweepExecuted(
    bytes32 indexed operationId,
    address indexed vault,
    address indexed token,
    address destination,
    uint256 amount
);
```

但是链上事件只证明执行了某笔归集，不证明资金已通过合规审查。风险决策的证据必须保留在独立的链下系统中。

### 4.3 具体方案：资金池按资产建立风险预留

如果调查初步确认 1,000 USDT 应予预留，系统可以生成：

```
Risk Case:         CASE-001
Asset:             USDT
Pool:              Treasury A
Exposure:          1,000 USDT
Reserve:           1,000 USDT
Risk Status:       ACTIVE
```

随后：

```
Treasury 链上余额：     1,000,000 USDT
风险预留额度：              1,000 USDT
其他运营预留：              5,000 USDT
------------------------------------
内部可调度上限：          994,000 USDT
```

这个例子只说明内部资金调度算法，不代表法律上允许剩余 994,000 USDT 无条件转出。

最少需要两个独立约束：

\\[ \text{Spendable}\_{token} \leq \max(0, B-H-R) \\]

其中：

- \\(B\\)：链上余额。
- \\(H\\)：冻结及风险预留。
- \\(R\\)：其他运营和流动性预留。

但还应另有：

```
legal_hold_enabled
asset_withdrawal_paused
pool_withdrawal_paused
```

一旦触发法律层面的禁止转出，即使计算出的可调度余额大于 0，也必须拒绝不符合条件的提现。

这种设计可以同时支持“精确金额风险预留”和“整个资产或资金池暂停”，避免把两个不同性质的控制混为一谈。

### 4.4 是否应该将这 1,000 USDT 从 Treasury 转到隔离钱包？

分情况。

| 情况              | 推荐方案                    |
| --------------- | ----------------------- |
| 只是初步告警，尚未确认     | 暂停相关资产流出，复核，不立即移动资金     |
| 确认需要冻结且不得转移     | 保留原位置并施加有效冻结控制          |
| 法规或有效指令允许集中隔离保管 | 双人审批后转入 QuarantineVault |
| Token 已被发行方冻结   | 保留原地，协调发行方和相关机构         |
| 资金已部分用于其他提现     | 追踪后续流向，依法处理敞口和可能的追偿     |

这里不存在通用的“把黑钱转到隔离钱包就能解除主钱包污染”的技术保证。

因为同一资金池中的同质化 Token 无法从合约层面按充值来源识别。是否可以通过特定金额的转移完成法律意义上的资产隔离，取决于有效的资金追踪证据和适用规则。

因此，我会把从 Treasury 向 QuarantineVault 转移风险资产设计成严格审批的特殊处置交易，而不是自动化归集策略。

### 4.5 如果发现时，资金池已经发生提现了怎么办？

这是比“已归集、未使用”更严重的事故。

假设：

```
Treasury Pool A

初始余额：1,000,000 USDT

收到风险归集：
    +1,000 USDT

随后正常业务提现：
    -600,000 USDT

余额：
    401,000 USDT
```

此时后续的 600,000 USDT 提现中，是否包含最初 1,000 USDT 的风险资金？

仅凭 ERC-20 的余额和转账记录，无法为每一枚同质化代币确定唯一的来源归属。

平台应该启动链上交易追溯、账务调查及法律分析，而不是简单通过金额相减就判断某个提现用户收到了黑钱。

处理要求是：立即控制剩余风险敞口，建立完整交易时间线，核查是否有受到影响的提现目标，保全证据，并根据适用规定决定后续报告、冻结、追偿或赔付安排。

如果因为归集后发现风险，导致流动性不足或者触发发行方对地址的限制，平台还必须启动业务连续性方案，而不应让其他租户无感地承担这笔损失。

所以，V2.1 架构的重点必须是让严重风险资金尽量在进入共享 Treasury 之前就被识别，降低事后无法完全挽回的风险。

建议的 Solidity 接口模型：

```
struct SweepPermit {
    bytes32 walletKey;

    address vault;
    address token;
    address destination;

    uint256 amount;
    uint256 expectedBalance;

    bytes32 riskDecisionId;

    uint256 nonce;
    uint256 riskEpoch;
    uint256 deadline;
}

interface IVaultManager {
    function sweep(
        SweepPermit calldata permit,
        bytes calldata signature
    ) external;
}
```

接口仅表示架构约束。正式实现还需要签名验证、Nonce 消耗、权限校验、重入保护、异常 Token 处理以及安全审计。

其中：

| 参数                | 作用             |
| ----------------- | -------------- |
| `walletKey`       | 绑定对应用户合约       |
| `vault`           | 防止归集其他地址       |
| `token`           | 绑定归集资产         |
| `destination`     | 限制归集目标         |
| `amount`          | 限制本次转移金额       |
| `expectedBalance` | 防止检查后余额发生非预期变化 |
| `riskDecisionId`  | 关联链下合规审查记录     |
| `nonce`           | 防止重复授权使用       |
| `riskEpoch`       | 允许撤销以前签发的授权    |
| `deadline`        | 限制授权有效时间       |

EIP-712 的 Domain 还应包含 `chainId` 和 Manager 地址，防止跨链和跨合约重放。

### 5.2 Risk Registry 与 SweepPermit 双重校验

我不建议只使用签名，因为签名一旦发出，在过期之前就可能被 Relayer 提交。

例如：

```
10:00  正常风险审核通过
10:01  签发 SweepPermit
10:02  发现资金来源涉及严重风险
10:03  原 Permit 尚未过期
10:04  Relayer 提交旧 Permit
```

如果没有撤销能力，就有可能把风险资金归集到正常资金池。

因此 Manager 必须同时验证：

```
签名合法
    AND
授权未过期
    AND
Nonce 未使用
    AND
风险版本有效
    AND
Vault/Token 未被冻结
    AND
Destination 属于授权资金池
    AND
资产余额与审核条件一致
```

一个可行的合约接口：

```
interface IRiskRegistry {
    function isSweepBlocked(
        address vault,
        address token
    ) external view returns (bool);

    function riskEpoch(
        address vault,
        address token
    ) external view returns (uint256);
}
```

这里还有一项重要优化：

不需要为几百万个正常用户都写入链上风险状态。

默认没有 HOLD 标记的地址，可以在提供有效 SweepPermit 时执行归集。

只有被标记的 Vault/Token，才需要额外的链上冻结状态，并支持解除、提高版本号或撤销旧授权。

不过这也存在两个限制：

第一，Risk Engine 识别到风险，并不意味着链上的冻结交易已经生效。在风险事件与链上冻结确认之间，可能存在交易抢跑。

第二，即使 `expectedBalance` 相同，也不能证明资产来源完全相同；标准 ERC-20 的余额不承载充值来源信息。

所以，还需要在执行前重新检查最新链上事件、重新模拟归集并缩短授权有效期。即便如此，异步 KYT 与公开区块链之间也不可能实现绝对无竞态的风险隔离。

高风险资金应进入专门处理通道，不能仅依赖普通归集流程中的最后一次余额校验。

### 5.3 不应该允许任意切换归集目的地

建议 Manager 对目标地址进行明确约束。

```
NORMAL_SWEEP
    → 已授权 ClearingVault

TREASURY_SETTLEMENT
    → 已授权 TreasuryVault

RISK_DISPOSITION
    → 经特殊授权的隔离保管或合法处置地址
```

`RISK_DISPOSITION` 必须使用与普通 Sweep Operator 不同的权限，由合规审批、资金控制权限及必要的多签共同控制。

不能在普通 `sweep()` 中提供任意 `destination`，然后仅依赖服务端判断它是否安全。

即使目标地址已经包含在 EIP-712 签名里，合约仍应检查目标是否属于该操作类型的允许范围。

## 六、进一步解决污染问题：两级资金池还是三级资金池？

我的建议是 三级逻辑隔离，按业务风险等级选择是否进行二次链上转移。

### 6.1 一级：DepositVault，原始资金隔离

特点：

每个用户拥有独立 Vault，或者大额业务按充值订单生成独立 Vault。

充值在这里完成初次 KYT、身份关系检查、风险筛查和最终性确认。

这一级的核心目标不是资金利用率，而是防止高风险入金过早进入共享资金池。

### 6.2 二级：ClearingVault，已初审资金缓冲区

只允许已经完成初次风险审核的资产进入。

它的价值在于：

- 已审核资产可以集中管理，不需要每次都立即转入高流动性热钱包。
- 可以设定短暂的观察窗口，接收延迟告警或风险情报更新。
- 如果事后发现高风险入金，可以先在这个较小的资金池内控制影响范围。
- 可以按租户、资产、风险级别和结算周期隔离。

但需要指出，ClearingVault 并不能保证其资金永远没有风险。 风险情报可能在资金转出之后更新，而且其他地址仍可以直接向 ClearingVault 转入 ERC-20。

ClearingVault 只能降低风险扩散的概率与范围，无法提供绝对纯净证明。

### 6.3 三级：TreasuryVault，正式支付资金池

Treasury 主要承担外部提现、内部资金调拨与热钱包流动性管理。

对于已经满足风控和结算要求的资金，才可以进入。

为了节约 Gas，可以根据风险等级采用不同策略：

| 资金等级     | 推荐资金路径                                           | 成本     |
| -------- | ------------------------------------------------ | ------ |
| 低风险、可信业务 | DepositVault → Treasury                          | 较低     |
| 普通零售用户   | DepositVault → ClearingVault → Treasury          | 较高     |
| 大额、高风险业务 | 独立 DepositVault → 独立 ClearingVault → 专用 Treasury | 最高     |
| 已命中严重风险  | 保留在 DepositVault，等待处置                            | 无须立即归集 |

不建议全系统无差别地执行两次链上归集。

应该让 Risk Engine 决定正常资金是否能够跳过 ClearingVault，同时强制高风险场景使用更严格的隔离路径。

安全上不应该仅按用户等级决定，而应综合本次充值来源风险。 一个历史上完全正常的用户，也有可能突然收到来源异常的资金。

## 七、最难的问题：风险发现延迟与持续监控

即使首次 KYT 审核通过，也不能保证一笔充值永远安全。

例如：

```
10 月 1 日：用户充值 1,000 USDT
10 月 1 日：KYT 判定正常
10 月 1 日：平台完成归集和入账

10 月 5 日：链上风险数据库更新
10 月 5 日：来源地址被识别为可疑案件关联地址
```

或者资金已经正常归集了几个月，才收到有关部门的正式通知。

因此 KYT 不应该只是一次性同步 API。

必须设计成历史交易持续监控系统。

FATF 在 2026 年 7 月的虚拟资产监管更新中，继续强调虚拟资产服务提供者需要完善风险缓释、监管实施与可疑活动防控。

### 提现也必须进行 KYT

不能仅检查充值来源。

所以应该分别进行入金 KYT 与出金 KYT，并建立用户整体风险档案。

## 八、Ledger 如何处理黑钱，以及如何避免污染其他租户？

这里建议引入 Risk Hold Ledger。

原 Ledger 的简单结构：

```
AVAILABLE
FROZEN
WITHDRAWAL_RESERVED
```

还不够。

推荐区分：

| 余额类型                  | 业务含义            |
| --------------------- | --------------- |
| `PENDING_DEPOSIT`     | 链上已经发现，尚未满足确认条件 |
| `RISK_PENDING`        | 等待风险分析，不可使用     |
| `AVAILABLE`           | 可进行合法业务操作       |
| `USER_HOLD`           | 普通业务冻结          |
| `COMPLIANCE_HOLD`     | 合规风险控制          |
| `WITHDRAWAL_RESERVED` | 提现预留            |
| `SETTLED`             | 已经完成相关账务结算      |

这些可以是业务余额分组或账务子科目，但基础财务分录必须继续保持借贷平衡。

### 场景一：未入账时发现风险

例如用户转入 1,000 USDT。

Ledger 不应直接增加可用余额，而应先记录待处理的托管资产和相应受限制负债。

直到风险检查和链上最终性条件通过后，再将其转为用户可用余额。

这样风险资金不会成为可以立即提现的客户余额。

### 场景二：已经入账，之后发现风险

需要执行独立的补充控制：

```
用户原可用余额：  5,000 USDT
发现风险敞口：    1,000 USDT

合规冻结：        1,000 USDT
剩余可用：        4,000 USDT
```

这是资金余额足够、风险范围允许精确冻结时的简单例子。

如果用户已经把余额全部提现，不能简单将用户余额改成负数就认为事件已经处理完毕。

此时涉及真实资金敞口、潜在追偿、风险准备金、报告义务及损失处理。不能把已经造成的经济损失藏在 Ledger 的一个负数里。

### 多租户账本必须和资金池绑定

建议新增：

```
tenant_id
user_id
asset_id

source_deposit_id
deposit_vault_id

treasury_pool_id
risk_case_id

risk_status
hold_amount
```

在共享 Treasury 模式下，一个风险事件可能同时涉及资产控制和租户债权，但二者不能混淆。

例如租户 A 用户的充值存在风险，通常不应该无理由地把租户 B 的正常用户账务余额全部冻结。

如果共享资金池面临真实的发行方地址冻结或法律处置风险，则又不能仅靠账本隔离就假装租户 B 的资金毫无影响。

因此多租户架构应优先让高金额或高风险租户使用独立 TreasuryPool，并明确资金池损失承担、资产隔离和业务连续性规则。

## 九、需要额外考虑的三种特殊情况

### 9.1 有人故意向 Treasury 发送少量黑钱

这种行为可能是为了制造风险告警、干扰平台正常运营。

例如：

```
恶意地址
   │
   └── 直接向 Treasury 转入 0.01 USDT
```

Treasury 合约通常无法阻止标准 ERC-20 直接转入。

因此不能规定“只要 Treasury 出现一笔风险关联 Token，整个系统永久冻结”，否则平台可能遭受恶意资金投递造成的拒绝服务。

但也不能单纯因为金额小就忽略真正的制裁命中。

正确设计应综合法律义务、风险可靠程度、直接或间接关联、金额、资金归属和实际影响范围，由风险策略及合规人员决定精确冻结还是扩大暂停。

对于无法匹配平台归集任务的直接入金，应登记为 `UNATTRIBUTED_INBOUND`，不得自动给任何租户记账，也不能自动当作可用平台资产。

### 9.2 Token 发行方冻结了整个 Treasury

例如某个稳定币发行方对资金池地址实施限制。

此时：

- 平台自己的智能合约权限无法解除发行方 Token 合约实施的冻结。
- 不能保证通过部署一个新 Treasury 就能够转移旧池的资产。
- 链下 Ledger 的账务记录无法代替真实的链上流动性。
- 应启动受影响资产的应急预案，并依据相关规则与发行方、客户、监管机构协调。

这说明资金池隔离不仅是 AML 问题，也是资产发行方权限风险和流动性风险问题。

### 9.3 一笔黑钱导致用户充值地址不再适合继续使用

我建议支持 `DEPRECATED` 或 `RETIRED` 地址状态。

例如：

```
旧 DepositVault A
    └── 风险资金留存，禁止普通归集

新 DepositVault B
    └── 重新分配给已通过审核的后续业务
```

新地址可以减少后续正常充值和旧 Vault 中风险资产的直接混合。

但必须注意，地址更换不等于用户、资金或关联风险自动解除。仍需要适当的账户审查，也不能使用地址轮换规避制裁、冻结或调查。

另外，旧地址永远可能收到外部转账，所以 Indexer 不能因为它已经弃用就停止监控。

这条历史对安全审计、责任分析和后续合法处置非常重要。

## 十一、生产环境的关键测试用例

| 测试场景                         | 必须验证的结果              |
| ---------------------------- | -------------------- |
| 黑钱转入未部署的 Vault               | 不触发自动部署和归集           |
| 黑钱转入已部署的 Vault               | 风控 Hold 生效后，普通归集被拒绝  |
| 同一 Vault 同时持有正常和风险 USDT      | 不允许未经审查把全部余额扫入正常资金池  |
| 归集授权签发后风险升级                  | 已撤销或失效的授权不能继续执行      |
| Risk Engine 故障               | 未获得有效新授权的归集默认暂停      |
| 余额在审核和归集之间变化                 | 不符合授权余额条件的归集失败       |
| 黑钱已进入 ClearingVault          | 能暂停受影响的清算池           |
| 黑钱已进入 Treasury               | 能追踪原始充值并紧急限制资金池出金    |
| Treasury 在风险告警前已经发生提现        | 能生成资金流分析报告和待处理风险敞口   |
| Treasury 收到未经授权的 ERC-20 直接转账 | 不得自动给用户入账            |
| 发行方冻结 Treasury               | 能正确识别不可用余额并启动应急流程    |
| 多租户共享资金池                     | 可识别具体租户风险敞口和资金池影响范围  |
| Risk Hold 解除                 | 需要有效审批、审计和重新检查       |
| 恶意地址向 Vault 投递小额风险资产         | 不得绕过审查，也不能自动永久封禁整个平台 |

还有两项必须单独进行故障演练：

归集与风控竞态测试。 在旧 SweepPermit 已签发、冻结交易尚未确认时，模拟 Relayer 抢先执行，确认系统对这种竞态有明确的防护策略和事故恢复路径。

事后污染回溯测试。 在风险资产已经经过 ClearingVault、Treasury 和多笔正常业务提现之后，再引入延迟风险告警，验证能否准确追踪资产流、影响范围、账务敞口和受影响订单。

这两项不能只通过单元测试验证，应在完整本地 EVM 环境中模拟链上执行。

## 十二、最终架构建议

经过这次调整，我会把原方案升级为：

CREATE2 DepositVault

每用户或每充值订单独立收款

KYT + ComplianceEngine

持续审查 · 资金来源 · 风险冻结

RiskAuthorizer + RiskRegistry

审批签名 · 撤销 · 链上冻结

VaultManager

有条件的批量归集 · 统一 Gas

ClearingVault

可选清算缓冲池

Risk Hold / Quarantine

风险隔离与合法处置

Isolated Treasury Pools

分租户/风险域资金池 · 出金硬限制

Withdrawal Engine + Ledger

提现风控 · 双重记账 · 资金追溯

### 我的最终技术判断

我建议坚持以下三个架构决定：

1\. 每个用户独立 DepositVault 仍然保留，但要支持每充值订单独立地址。 这是降低风险资金与正常资金在第一环节发生混合的最有效架构手段之一。

2\. 普通归集必须获得风险授权，并由链上强制执行授权边界。 归集是资金进入共享池的重要入口。只靠链下 Scheduler 进行检查，不足以构成可靠的生产安全边界。

3\. 不再建立单一超大 Treasury，而是采用风险分级、资产隔离、可暂停的资金池模型。 已归集风险资金的处理不能依赖所谓“自动洗净”，必须建立完整的资金追踪、冻结、合法隔离和应急机制。

其中我尤其建议将这条规则写入整个钱包平台的最高级别设计约束：

任何未完成必要风险审查的充值，不得被当作正常可用资产自动归集到共享提现资金池；任何事后发现的重大风险资金，都必须能够追溯其链上流向和账务归属，并快速控制其继续流出。

这样才能在保持 CREATE2 合约地址、无需向用户地址补 Gas、批量归集优势的同时，把黑钱引起的资金池风险控制在尽可能小的范围内。
