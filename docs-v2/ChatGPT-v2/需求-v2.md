- 问： “2. 观察期内提现必须受到风控约束” 这里我们的处理方案是，用户自己充值进来的币，还未归集的情况下即使是黑的用户也能提取走，这个提取过程不涉及热钱包（池）也不需要多签。
  “3. 热钱包 100,000 USD 上限不是天然的链上硬限制”：这里需要根据币种类型分别配置最大上限，提供可修改API。

这两处需要调整，而且会影响 Wallet Platform 的资金流转模型。

## 1. 观察期内允许用户直接提现

按照你的方案，观察期限制的是平台向热钱包归集，不限制用户提取自己尚未归集的资金。

更新后的业务规则：

- 用户充值至自己的 `DepositVault` 合约。
- 资金在观察期内暂存，不进入热钱包池。
- 用户可以直接申请提现未归集资金，不需要等待观察期结束。
- 提现由 `DepositVault.withdraw()` 直接转出，不经过 `HotVault`，也不需要多签。
- 如果资金来源被标记为高风险，平台不执行自动归集；但按你的业务设定，未归集资金的提现权限不因这一内部风控标签而自动取消。

这里有两个不同的概念：平台内部将资金标记为高风险，不代表该资产在链上一定被冻结。如果 USDT、USDC 等代币发行方已经冻结了相关地址或资产，充值合约也无法绕过代币自身的转账限制。同时，实际部署仍需满足适用的制裁、反洗钱和司法冻结义务。

## 2. 热钱包额度改为按币种独立配置

不再将固定的 `100,000 USD` 作为所有币种共用的唯一上限。

建议使用以下配置结构：

`(chain_id, token_address) → max_balance`

例如，下面数值仅用于说明配置方式：

| 链        | 币种   | 单个 HotVault 最大余额 |
| -------- | ---- | ---------------- |
| Ethereum | ETH  | 20 ETH           |
| Ethereum | USDT | 50,000 USDT      |
| Ethereum | USDC | 50,000 USDC      |
| Ethereum | WBTC | 1 WBTC           |
| BSC      | BNB  | 100 BNB          |

每个热钱包合约可以同时持有多个币种，各币种分别校验对应额度。原有的总 USD 敞口上限可以保留为可选的第二道风险阈值，但不应替代币种额度。

配置通过平台管理 API 修改，再由链上 `HotPoolManager` 或独立额度配置合约执行。修改完成后，对后续归集生效；如果新额度小于现有持仓，应暂停该币种新增归集并进入容量回收流程，而不是强行撤销已有充值。

```

请求示例：

```
{

## 5. 还有两个实现边界需要注意

第一，用户直接提现不需要多签，但仍然需要授权。

因为你的项目是中心化平台，如果用户没有自己的链上私钥，可以采用平台身份认证 + 单个提现授权签名 + Relayer 支付 Gas 的机制。

Relayer 可以参考 ERC-2771 元交易设计。

[image](https://www.google.com/s2/favicons?domain=https://eips.ethereum.org\&sz=32)

Ethereum Improvement Proposals

&#x20;用户资金从 `DepositVault` 直接转出，独立 Gas 账户支付手续费，整个过程不涉及热钱包池资产。



第二，旧充值合约退役时要明确剩余资产的处理规则。

你要求旧地址一旦 `RETIRED` 就不再提现，这意味着合约中尚未提走的资金可能长期滞留。建议在实现中明确 `ACTIVE → RETIRED` 状态切换时的剩余余额检查，以及这些资产的法律和运营处置规则。

另外，热钱包轮换时应优先寻找最旧且持有目标币种、能够释放所需容量的健康 HotVault。这样才能避免清空一个不相关币种的热钱包，却仍然无法接收当前待归集资金。

这版已经将用户未归集资产直接提现和平台自动归集作为两条独立资金路径，后续可以据此继续细化 Solidity 合约及 Rust 后端接口。
