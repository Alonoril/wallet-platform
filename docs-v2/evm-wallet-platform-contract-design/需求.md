# EVM-Chain端

-EVM链Wallet-platform设计需求：1.
用户的充值地址不是传统的助记词派生地址，而是使用充值管理合约为每个用户创建的唯一充值合约（这个合约支持充值，充值的币不立马归集而是有一短时间的观察期，观察期间充值地址没有问题才归集到热钱包，未归集的币是支持用户自己提现的），这个合约地址如果被“黑钱”污染或者是被冻结了可以生成一个新的合约地址，旧的合约如果还收到充值则不管（不再支持用户的提现，后端服务也不再监听这个地址）；2.
热钱包资金池也是由资金池管理合约生成的：资金池管理合约最多生成20或50个热钱包合约；按链和币种分别配置每个热钱包的最大持仓数量，并提供查询、修改上限的API。如果当前币种在所有健康热钱包中的可用容量都不足，则将最旧且风险正常的热钱包中的相应币种转入冷钱包，释放容量。冷钱包私钥由最高权限人掌控，不会出现在合约和系统任何一个地方。原10万USD统一估值上限调整为按币种配置的数量上限。

# EVM Wallet Platform — 智能合约钱包架构与业务流程图

根据你的需求，建议采用 双 Factory 合约 + 用户独立充值合约 + 热钱包合约池 + 离线冷钱包 的架构。

核心设计原则：

- 充值隔离： 每个租户用户拥有独立充值合约地址，污染后通过版本升级生成新地址，旧地址退出业务。
- 观察期： 充值不立即归集；风控与观察期约束归集。用户自己充值且尚未归集的币，即使用户被标黑也允许从自己的充值合约直接提走，无需多签，也不经过热钱包池。
- 热钱包池： 最多创建 20 或 50 个热钱包合约；按 tenantKey、chainKey、assetKey 配置各币种的最大持仓数量，支持授权管理 API 查询和修改。
- 冷钱包归集： 热钱包池满额时，优先将最旧且风险正常的热钱包资金转至冷钱包，释放容量。
- 风险隔离： 区分归集前和归集后发现黑钱，避免问题资产继续进入其他资金池。

整个设计中，合约负责资产控制和权限校验，链下 Wallet Platform 负责链上监听、风控、观察期调度和交易发起。

## 需要重点明确的设计细节

1\. 充值地址退役并不等于链上地址失效

建议使用 `DepositFactory + CREATE2 + version` 为同一个用户生成新的唯一充值合约。

[image](https://www.google.com/s2/favicons?domain=https://eips.ethereum.org\&sz=32)

Ethereum Improvement Proposals

&#x20;旧合约进入 `Retired` 状态后，禁止提现和归集，后端停止业务入账监听。但是，不能阻止别人直接向旧地址转入
ERC20，因此必须保留异常资金处置方案。

2\. 未归集充值允许用户直接提现，风控约束归集与热钱包提现

用户自己充值、仍留在其 `DepositVault` 中且尚未归集的币，允许由用户本人授权直接转到指定地址；观察期未结束、来源风控未通过或用户被标黑，均不构成平台拒绝这条自提路径的理由。参考 [ChatGPT-v2](../ChatGPT-v2/需求-v2.md)，集中式平台默认采用“平台身份认证 + 专用单签授权 + Relayer 支付 Gas”，不要求用户持有 EVM 私钥。资金直接从该用户的充值合约付出，不进入或借用热钱包池，也不需要 Milon 多签、验证节点批准或跨链提现证书。

平台先核验用户身份及钱包归属，专用 `REFUND_SIGNER` 对本次自提签发一份授权；EVM 合约核验签名、walletKey、币种、金额、收款人、nonce 与有效期，防止他人冒领和重复提款。该签名用途与热钱包提现门限签名分开，Gas Relayer 只提交交易。直接提现与归集使用同一充值合约实际剩余余额和资产状态 nonce，在 EVM 交易中原子执行；先成功的一方减少余额并使另一份旧授权失效。

为避免同一笔钱自提后又从热钱包提走，未归集余额仅作为 EVM 待归集余额展示，不提前计入 Milon 的 available、withdrawalHeld 或 riskHeld；实际归集最终确认后，桥服务才按净归集金额生成可用权益。已归集资产的提现继续经过 Milon 多签与热钱包出金风控。

平台风控标黑与地址退役分别处理：标黑只禁止归集，不自动关闭未归集自提；确认为 Retired 的旧地址仍遵循第 1 项停用规则。代币发行方在代币合约内实施的冻结，仍受该代币自身转账规则限制。拟新增直接提现入口的详细授权与对账规则见[三段映射设计第 5.1 节](20261011-evm-rust-milon-mapping-and-bridge.md#51-未归集余额的用户直接提现)。

3\. 热钱包按币种配置最大持仓上限，并提供修改 API

每个租户、每条 EVM 链、每个 assetKey 单独配置 `maxBalanceRaw`，该上限应用于池中每个热钱包的对应币种，不再使用统一 100,000 USD 上限。原生币与 ERC20 分别识别，同名币在不同链上分别配置；上限使用该资产最小单位的 uint256 整数，API 以十进制字符串传递，禁止浮点金额。

`wallet-platform-rust` 提供查询与修改入口：

```text
GET /v1/admin/chains/{chainId}/hot-pool/token-limits
PUT /v1/admin/chains/{chainId}/hot-pool/token-limits/{tokenAddress}
```

修改请求包含 `max_balance_raw`、`enabled`、`expected_cap_version` 和变更原因；租户从已认证上下文确定，仅授权租户管理角色可提交。chainId 与 tokenAddress 解析到已登记 chainKey/assetKey，原生币使用零地址标识。API 记录审计并按既有治理权限提交链上配置，返回配置作业状态；以 EVM 配置最终生效为准，数据库修改成功不等于链上限额已变更。接口字段、并发控制与生效流程见[三段映射设计第 4.3 节](20261011-evm-rust-milon-mapping-and-bridge.md#43-热钱包按币种限额与修改-api)。

受控归集和补仓执行时，合约检查目标热钱包该币种实际余额加本次转入金额不超过当前上限；后端同时预留待归集容量。未配置、未启用或上限为 0 的币种禁止新增受控转入。下调到现有持仓以下时，不扣减用户权益，暂停该币种新增归集并按既有风控规则释放容量。转冷优先选择最旧且持有目标币种、能释放所需容量的健康热钱包。外部仍可直接向热钱包转账，因此保留余额监控和异常超额处理。

4\. 冷钱包私钥完全不需要参与归集

`HotVault` 合约只需知道冷钱包的公开地址，归集交易由授权 Relayer 发起并支付 Gas。冷钱包只接收资金，私钥不进入 Wallet
Platform、热钱包合约或充值合约。

建议使用多签、分级权限和紧急暂停能力控制敏感操作。

5\. 归集后发现黑钱是必须重点控制的风险

一旦污染资金进入某个 HotVault，应停止该热钱包后续出金和转冷操作，并追踪受影响资金。如果已经归集到冷钱包，则只能通过离线隔离和合规处置处理，无法撤销已经确认的链上转账。

这套方案中，最值得进一步细化的是 DepositVault、DepositFactory、HotVault、HotPoolManager
四种合约的接口、权限模型与资金状态机。这将决定观察期、用户提现和污染资金隔离能否真正由合约强制执行，而不是仅依赖后端数据库状态。

## Milon 链审批与 EVM 提现补充需求

已经归集的资产提现在 Milon 链发起，由指定验证节点组成的提现审批委员会完成链上多签。审批交易成功执行并取得 Milon
用户块终局证书后，节点独立核验审批记录，使用各自独立的跨链签名密钥为同一提现授权出具签名。`wallet-platform-rust` 收集签名并支付
EVM Gas，调用指定热钱包合约；EVM 合约自行验证门限签名、订单唯一性、授权有效期、风险状态和资金限额，再向已审批的收款地址付款。

Milon 已有 MIP-25 账户多签，因此复用 `VoteInit / Vote / vote-gated execute`，新增提现业务 App 管理订单、余额预留、审批和结果回执。后端的
RPC 查询结果不能直接替代 EVM 合约验签；Milon 共识签名也不能直接当成 EVM 提现签名。

完整方案、代码依据和异常恢复规则见 [Milon 链多签与 EVM 安全提现设计](20261011-milon-multisig-evm-withdrawal-design.md)。

未归集充值按上文第 2 项直接从 DepositVault 自提，独立于这条 Milon 审批路径。

已归集资产的提现流程为：

1. Milon 受理并预留余额：保存唯一订单，绑定用户、资产、金额、费用和收款地址。
2. 节点链上审批：通过 VoteInit → Vote → vote-gated execute 执行 ApproveWithdrawal。投票 ready 后，还要确认业务执行成功及所在块终局。
3. 节点签发跨链凭证：各节点独立核验审批记录，用独立 ECDSA 密钥签署同一份提现证书。
4. Rust 后端提交交易：收集签名、支付 Gas，调用指定热钱包。
5. EVM 自行验签付款：验证门限、参数、期限、委员会版本、风险状态和限额，消费订单后转账。
6. 结果回到 Milon：EVM 付款最终确认后，通过可信回执结算余额预留。

当前 EVM 的 TenantAuthority 已支持 ERC-1271，可以接入新增的 MilonWithdrawalVerifier，让热钱包验证节点门限证书。ERC-1271
标准 (https://eips.ethereum.org/EIPS/eip-1271)

安全上需要特别补齐三点：

- 余额依据：节点必须独立验证用户授权和余额；多个节点查询同一个后端数据库，仍然依赖该后端。
- 跨钱包去重：所有热钱包共享订单消费簿，防止换池后同一订单再次付款。
- 取消屏障：Milon 请求取消后保留余额预留，等 EVM 禁付最终生效才能释放。

一期方案的信任边界是跨链签名委员会。若要求 EVM 直接证明 Milon 审批真实存在，还需实现 Milon 轻客户端及业务状态证明。

## EVM、Rust 桥接服务与 Milon App 的统一映射

桥接服务确定为 `wallet-platform-rust`：解析两条链的来源事件，维护链/租户/用户/钱包/资产映射，组织独立节点核验和签名，通过持久 Inbox/Outbox 中继消息，并等待目标链业务成功与终局后更新查询视图。

Milon 采用专用托管权益账本，保留 EVM 原始 uint256 金额；真实资产留在 EVM。未归集充值由 EVM 余额与后端来源记录展示，支持用户直接自提；实际归集最终确认后，才按每笔来源的净归集金额生成一次权益。用户可用权益、风险预留、提现预留与热钱包提现订单由 Milon App 原子维护，后端数据库保存其终局投影。归集后调拨、转冷和补仓只更新托管位置，不再次生成用户充值权益。

三段以稳定的 tenantKey、userKey、walletKey、assetKey、depositId、requestId 和 messageId 关联。充值观察与直接自提在 EVM → Rust 跟踪；归集权益走 EVM → Rust → Milon；热钱包提现批准走 Milon → Rust → EVM；付款或安全取消结果走 EVM → Rust → Milon，最后同步后端与用户通知。节点密钥与审批权保留在独立节点。

统一协议和流程图见 [三段映射与桥接设计](20261011-evm-rust-milon-mapping-and-bridge.md)，阅读入口见 [设计索引](README.md)。
